## Faculty study plans
- A plan is one JSON payload per faculty CMS target `facilities.<faculty>.study_plan` (`translations.ar|en.payload.plan.departments[].terms[].courses[]`), not relational tables.
- Admin editing is the visual board on each faculty admin page: `ManagesStudyPlanBoard` (Livewire actions) -> `FacultyStudyPlanBoardService` (pure payload edits) -> `CmsWorkflowService::saveDraft`. Board and form save independently; the form never carries departments.
- Bulk load from a curriculum: convert the source with a script in `database/seeders/Data/study_plans/`, then `php artisan faculty:import-study-plan <faculty> <file.json> --user=<id>` (dry run by default, `--write` saves an unpublished draft). It skips any plan editors have already saved or published (`--replace-edited` overrides, manual only); `cpanel-deploy.sh` runs it only when `study-plans.approved` is placed on the server (see `Docs/DEPLOYING.md`).
- Business 2026 plan: `study_plans/build_business_2026.py` writes `business-administration.json` (five programs, ids `hr`, `accounting`, `marketing`, `finance`, `mis`; the old `management` program is gone) and a report of every gap it filled. The live plan was already edited, so it loads only by a manual `faculty:import-study-plan business-administration … --replace-edited --write` (an unpublished draft to review and publish on the board).
- Shared courses: a course id is one course across the plan's programs. Every program holding it carries the same record (code, titles, hours, teachers, lectures, specification); only its term, row and prerequisites differ (a prerequisite edit applies where that course exists). The board's course panel picks a term per other program ("Also in these programs", `placements`), cards show a Shared badge, and Delete removes only the open program's copy (`FacultyStudyPlanBoardService::saveCourse`/`deleteCourse`).
- Public graph: `resources/js/alpine/studyPlan.js` (`planEdgePaths` is shared with the admin board in `resources/js/filament/studyPlanBoard.js`). Layout is measured from the DOM, not computed from constants.
- Course teachers: `courses[].teachers.{theory,practical} = {memberIds: [], enabled}` (faculty profile ids, never names; any number per part). Plans saved earlier hold one `memberId`, still read. Edited on the board's course panel (add/remove chips); the course page reads each name and photo from the public profile (`FacultyPageService::courseTeachers`) and skips a switched-off part. The older `instructor` field shows only when no teachers are set.

## Centers (Requirements Unit)
- A top-level section like About or Faculties: `/{locale}/centers` (every center as a card, plus "what the centers offer"), and per center (`config/centers.php`; only `requirements-unit` so far, template `requirements-unit`) `/centers/<center>` with three subpages: `staff`, `required-courses`, `elective-courses`. A center is part of the university, not a faculty: a manager instead of a dean, no projects, research or labs. Plan and as-built notes: `Docs/CENTERS_PLAN.md`.
- CMS targets (area `centers`, permission component `centers`; editors get it by migration): `centers.landing`, `centers.<center>`, `centers.<center>.staff`, `centers.<center>.courses` (one course list shown on both course pages). Admin: Centers › `ManageCenters` (target picker, draft/preview/publish; `?subpage=elective-courses` previews the elective list).
- Until published, each target shows `database/seeders/Data/centers/centers.json` and `<center>-courses.json`. The course list is built from the faculty study plans' `type: university` courses by `build_requirements_unit.py` (one course per subject with each faculty's own code in `faculties[] = {faculty, code, credits?}`).
- `CenterCatalogServiceInterface` (content, courses, validation, study plan links; no CMS service dependency, reads `cms_target_contents` itself) and `CenterPageServiceInterface` (public DTOs, previews, staff options).
- Staff are faculty profiles with no faculty and `faculty_members.center_slug` (picked in the profile admin); the staff page lists published ones, the page's `managerMemberId` (one of them) shows first and in the manager block, and their profile names the center. Course teachers are profile ids like the study plan's.
- Faculty link: a study plan course of type `university` gets `unitCourseUrl` (`CenterCatalogServiceInterface::studyPlanCourseUrl`): the unit course picked on the board (`requirementsUnitCourseId`), else the one listing this faculty and code, else the required or elective list. The public study plan modal and course page show it. Tests: `CentersPagesTest`, `AdminCentersWorkspaceTest`.
- Site search: source `centers` (`SearchIndexService::rebuildCenters` from `CenterPageServiceInterface::searchEntries`): each page and each course (linked to `#course-{id}`), in both languages; rebuilt after commit when a `centers.*` page is published or unpublished or a center staff profile is saved (`SearchIndexObserver`), and on every deploy. Test: `CentersSearchTest`.
- Header: Centers is the ninth top-level item, after Faculties, a plain link (migration `2026_11_02_000003_add_centers_to_header_menu`, `NavigationSeeder`). Nine labels fit from 1280px only because `navigation.css` shrinks them on a 1280-1535px ramp; a tenth item needs another layout change.

## Faculty final exams
- Every faculty has a `final-exams` page (`facilities.<faculty>.final-exams`, schedules with files or timetable rows). Live, only Medicine, AI, Petroleum and Business have a page row and card for it (from the old site); the others get it by default (`FacultyPageService::hasDefaultSubpage`), while a disabled row or hidden card keeps it off. Its card on the faculty and overview pages appears only once a schedule with a file or a row is published in that locale (`FacultyPageService::hasPublishedExamSchedule`); the page URL itself always opens, with an empty-state line until then.
- A schedule's timetable rows show as an interactive board like the study plan (`partials/exam-schedule.blade.php`, `resources/js/alpine/examSchedule.js`, `resources/css/frontend/exam-schedule.css`): a column per exam day (dates read as `Y-m-d` or `d/m/Y` go in date order, others keep the editor's order), year filter chips, search, a table view, an exam dialog listing that year's exams, and lines joining a year's exams (via `planEdgePaths`). Done/today/next-day badges use the visitor's own date, since pages are cached. Grouping is `App\Support\ExamScheduleBoard`.
- Admin timetable rows (`examRowsField`): the date is a date picker stored as `Y-m-d` (an older typed date that can't be read moves into the day text); the day may stay empty, and the board shows the date's weekday and `d/m/Y`. Rows can be duplicated, and "Paste from Excel" adds rows copied from a spreadsheet or Word table (`App\Support\ExamScheduleRows::fromPastedText`: tab, comma or `|` cells, an optional header line in Arabic or English sets the column order). Each schedule's files show as a download button beside its title ("تحميل البرنامج (PDF)" when the editor gives no label). Tests: `FacultyFinalExamsTest`, `ExamScheduleRowsTest`.

## Faculty master's program
- AI, Pharmacy and Petroleum (`config/faculty_subpages.php` restricts `master-program`): page `/{locale}/faculties/<faculty>/master-program`, target `facilities.<faculty>.master-program`. Like final exams and council it is a default subpage in code (no page row; a disabled row or hidden card keeps it off), and its card comes first in the faculty's highlights (and the overview's pathways) unless an editor's card for it places it.
- Until a version is published, the page shows the reviewed curriculum in `database/seeders/Data/master_programs/<faculty>.json` (rebuilt by the `build_<faculty>.py` script next to it); the admin editor starts from it too. `FacultyMasterProgramServiceInterface` reads it, builds the page and validates on publish (each course once, unique codes, prerequisites are other courses, the same courses in both languages). A course is known by its `id` (its code when it was saved without one); `code` is optional (Petroleum's courses have none), `elective` marks an option, and `credits` 0 means the source gives only hours. A term (semester or group) may state its `credits` and a `note` when students choose among electives; totals use the stated credits. Outcomes may carry a `group` (domain).
- Public view `partials/master-program.blade.php`; the semester board's lines and course dialogs are `resources/js/alpine/masterProgram.js` (reuses `planEdgePaths`).

## Search
- `App\Support\LenientSearch` is the matcher for list searches (faculty projects, student lists, alumni directory, research publications/projects/researchers): every word in any order, Arabic folding, no article or punctuation, near spellings against names and titles. Callers pass the item's text in both languages, so a search works on either site.
- Site search: each `search_documents` row also holds the other language's text and `alt_title_normalized` (rebuilt by `search:index` on every deploy); below 10 exact hits, near spellings of titles are added after them.
- `CachePublicPages` keys each route on its own query parameters; a list search must list `q` there or every search gets the first cached page.
- `FacultyStudyPlanEditorService` workspace methods (`buildWorkspace`, `mergeWorkspace`) belong to the removed per-term form and are unused by the app; `validationErrors` is still the validator.
- Tests are slow (Livewire pages take 5-10s each); run classes separately with `--filter`, and run long ones in the background.

## Faculty departments, programs and specializations
- The departments page (`facilities.<faculty>.departments`) lists academic departments (`items[]`, every faculty); a department is an administrative unit: `headMemberId` (a profile id of this faculty's staff) with an optional per-locale `headTitle` and `headOnCouncil` (default on), and `councilMemberIds` (its department council besides the head). `FacultyLeadershipServiceInterface::departmentsValidationErrors` checks they are this faculty's staff and match in both languages. Each department shows its programs and its council; there is no type badge and no study plan button of its own.
- Programs have the study plans: page `/{locale}/faculties/<faculty>/programs`, target `facilities.<faculty>.programs`, `programs[] = {id, level (bachelor|master|phd|diploma), title, summary, duration, departmentSlug, studyPlanProgramId, managerMemberId}`, edited once for both languages below the language tabs (`program_rows`). `managerMemberId` is the program director (مدير البرنامج / Program Director), a profile of this faculty's staff: shown on the program card, beside the program on the departments page, and as a position on their profile (`FacultyLeadershipService::programDirectors`). `FacultyProgramServiceInterface` builds and validates it. A default subpage in code (card after Departments). Until published it lists each study plan program (`plan.departments[]`, which are programs) as a bachelor program in the department whose stored `studyPlanDepartmentId` links to it, plus the master's program page (department from `config/faculty_subpages.master_program_department`). Departments keep `type`/`studyPlanDepartmentId` only as hidden legacy values for that default; they are no longer validated.
- Business and AI departments carry `specializationId` (their study plan program) in `faculty_structure.json`; Business MIS has no department. Staff profiles keep `department_id` and may add an optional `specialization_id` (a program id, validated against the faculty's plan; labelled Program). Plan and as-built notes: `Docs/FACULTY_DEPARTMENTS_SPECIALIZATIONS_PLAN.md` and "Client changes (2026-11-04)" in `Docs/FACULTY_LEADERSHIP_COUNCIL_PLAN.md`.

## Faculty deanship and council
- Page `/{locale}/faculties/{faculty}/council`, target `facilities.<faculty>.council`, the same in both locales: `positions[] = {id, positionSlug, memberId}` and `includeDepartmentHeads`. Every row is a position from the faculty's own list and a published profile of the faculty's own staff; exactly one dean. The admin edits it in one section below the language tabs (`council_positions`). Pages saved before the list (`type`, `title`, `onCouncil`, `councilMembers`) still read. The top section is "عمادة الكلية / Faculty Deanship" (never "قيادة الكلية").
- Positions list: `FacultyPositionServiceInterface` (`faculty_positions.faculty_id` + translations), per faculty: every method takes the faculty. Dean, vice dean and head of department are built in (code); a faculty's row with their slug renames them for that faculty only. Rows with no faculty (saved before 2026-11-04) still read where a page uses them and are offered only to a faculty whose council page uses them; editing one makes that faculty its own copy. Each position has a placement, `leadership` (deanship cards) or `council` (members list); the dean always leads. Head of department is never picked: heads come from the departments page.
- `FacultyLeadershipServiceInterface` builds the page, validates both targets and, on publish (`publishTarget`), makes the published dean the faculty's dean row on About › Leadership. Like final exams, a faculty with no `council` page row or card has the page in code (`hasDefaultSubpage`). The faculty dean block reads `deanProfileSlug()`; PersonResource locks a council-managed dean's profile.
- Rank and positions are shown apart: `faculty_member_translations.position` is the academic rank (أستاذ، أستاذ مساعد، مدرس), shown as "الرتبة الأكاديمية: …" / "Academic rank: …"; positions held come from `memberPositions()`/`positionsOfMember()` (council positions, departments headed, department council seats), one chip each. `ProfilePageDTO::position` is the positions, `academicRank` the rank. `faculty:match-positions` (dry run in every deploy log, write with `faculty-positions.approved`) moves typed leadership titles onto council drafts. View `partials/council.blade.php`, styles `resources/css/frontend/faculty-council.css`. Plan and as-built notes: `Docs/FACULTY_LEADERSHIP_COUNCIL_PLAN.md`.
- Wording: "أعضاء الهيئة التدريسية" (never "الهيئة الأكاديمية"); English "Faculty Members" / "Teaching staff".

## Public forms
- Forms are built in the admin (Contact → Forms, `FormDefinitionResource`) and stored in `form_definitions` (fields in `schema_json`, optionally in steps). `FormDefinitionServiceInterface` is the only reader; the six original forms are inserted by the migration from `database/seeders/Data/forms/built-in-forms.json`.
- Pages pick a form with `App\Filament\Support\FormPicker` (event `formId`, admissions/jobs `applicationFormId`, suggestions `form.formId`). The page prints the schema via `public.forms.dynamic-form` (`formKey`) and the Alpine store reads it; there is no form list in the JS.
- A form in use (a page picks it, or it has submissions) can't be deleted, only disabled. Submissions go to the inbox set on the form.

## Staff intake links
- Per-faculty link (`/{locale}/staff-intake/{token}`) where academic staff find their profile by name and send corrections or a new profile. Plan and as-built notes: `Docs/STAFF_INTAKE_LINK_PLAN.md`.
- Nothing a teacher sends changes a profile: it is a `staff_intake_requests` row until a reviewer approves it, and approval goes through the About-entity CMS draft/publish workflow. Every open, claim and submit is logged in `staff_intake_access_logs`. Admin access uses the `staff_intake_links.*` and `staff_intake_requests.*` permissions.
- Name suggestions use `App\Support\PersonName::matchRank()`; keep `tests/Unit/PersonNameMatchingTest.php` green when touching name matching (the merge and research services share it).
- Center links: a link (and its requests) can belong to a center from `config/centers.php` instead of a faculty (`center_slug`, `faculty_id` null). Same flow, but no department, and required are only the name, academic title, position and biography (AR and EN), email, phone, photo and CV (`StaffIntakeService::CENTER_REQUIRED`; office, specializations, profile links and education stay optional), and the profile it applies to has no faculty and the center's slug, so approval puts the person on `/centers/<center>/staff`. A profile in a faculty or another center is only a starting point for a new center profile (and a center profile only a starting point on a faculty link). Access is `center_staff_intake.view|create|update`, held by no default role (super admins only until a centers editor role exists). Admin: Centers › Center staff links / Center staff requests; the faculty screens never list them. Test: `CenterStaffIntakeTest`.

## One profile per person (faculty, leadership, research)
- The faculty profile (`faculty_members`) is the one record of a person's name, photo, bio, education, contact and links, in AR and EN. A leadership row (`persons`: dean, rector, ...) points at it with `persons.faculty_member_id` and adds only the role, quote, category, order and visibility. A leader who belongs to no faculty has a profile with no faculty (only editors without a faculty limit can save one).
- Every page reads a leader's identity through `PersonIdentityServiceInterface` (`publicIdentities`, `profileMemberIds`, `personIdsForMember`). It still honours the older `faculty_members.person_id` link. Until `people:unify` has run, a field the profile leaves empty shows the row's old copy.
- The profile address is `/about/profile/{member-slug}`. A leadership slug, `?source=`, `/profile/person/...` and staff `-rN` researcher pages 301 to it (`ProfilePageService`). The sitemap and search list the profile, not the row.
- Research: a register row with `faculty_member_id` shows the profile's name (`ResearchPageService::researcherName`). Only external co-authors use `researchers.full_name`. The name-based staff suggestions (`ResearcherAdminServiceInterface::staffSuggestions`, the "Suggested" filter, `researchers:link-staff`) are how a researcher joins a profile, and they stay.
- Admin: the leadership editor (PersonResource) picks the profile and hides name, photo, bio, contact and education. Publishing it writes only role fields and leaves the row's old columns as they were (`AboutEntityCmsService::publishLeadershipRole`). There is no link or unlink action.
- `people:unify` (`PeopleUnifyServiceInterface`) ties existing rows to their profile. It never overwrites faculty-member data. Its dry run is in every deploy log, and the write runs only with `people-unify.approved` (see `Docs/DEPLOYING.md`). `people:merge` only merges duplicates now, including a leader's no-faculty profile into their faculty profile (the leadership row follows); its dry run is in every deploy log and the write needs `people-merge.approved`. Staff intake treats a no-faculty profile as the link faculty's own, so approving updates it. Plan: `Docs/PEOPLE_SINGLE_PROFILE_PLAN.md`.

## Graduates and top students import
- Each semester faculties send council decisions (.docx) listing graduates and top students. Editors import them from the faculty's Alumni / Honor List admin page ("Import from decision"): upload, review, confirm, and the rows are live. Plan and as-built notes: `Docs/STUDENT_LIST_IMPORT_PLAN.md`.
- `StudentListImportServiceInterface` does all reading and writing; the parsing is in `app/Support/StudentLists/`. Students are matched on university ID (`student_identifier`), so a re-import updates. Every import is a `student_list_imports` row that can be undone, newest first.
- Access is publish on that faculty page (`canManageTarget(..., 'publish')`), not a separate permission.
- Real decision files name real students: never commit them. Tests build look-alike files with `tests/Support/DecisionDocxFactory.php`.

## Events, announcements and news

## AI assistant (chat robot)
- Floating 3D robot + chat panel on public pages (`public/layout/chatbot.blade.php`, `resources/js/chatbot/*`), answering only from files uploaded under Administration › AI assistant (`ManageChatbot`, permission `chatbot.view|update`). RAG runs in Laravel: OpenAI embeddings + cosine over `chatbot_chunks`, answers from the Responses API with structured output `{category, answer}`. Full notes: `Docs/AI_ASSISTANT.md`.
- Main model `gpt-5.4-mini` (free daily tier), fallback `gpt-6-luna`. Model ids contain dots: read `config('chatbot.models')[$id]`, never a config dot path.
- Loading: the launcher is plain HTML/CSS shown from the first paint (`html.js`); `chatbot/bootstrap.js` fetches `chatbotWidget.js` + `chatbot-panel.css` on the first interaction only, so nothing of the assistant is on a page's critical path. Keep panel styles in `chatbot-panel.css`, not the main bundle.
- `/llms.txt` and `/.well-known/ard.json` (Lighthouse Agentic Browsing) come from `AgentDiscoveryServiceInterface`, built from the published header menus and footer contacts; text in `lang/*/agents.php`. Test: `AgentDiscoveryTest`.
- Misuse protection is layered (`ChatbotGuard`, moderation, model category, output guard, signed history, fair use per session + IP, escalating pauses); keep `tests/Unit/Chatbot/ChatbotGuardTest.php` (real questions must pass) and `ChatbotFairUseTest` green when touching it.

## Admin dashboard and visitor statistics
- The dashboard is widgets discovered from `app/Filament/Widgets` (views `resources/views/filament/widgets`, styles `.spu-dash-*` in `resources/css/filament/admin.css`, text `lang/*/admin_dashboard.php`): today's visitors, page views, people on the site now and people who talked with the AI assistant; a work queue (`NeedsAttention`: new form submissions and contact messages, staff requests, unpublished drafts of the last 60 days, scheduled publishing, missing pages, assistant failures, failed jobs, locked accounts; each only for a user who can act on it, inbox counts from each resource's own query); a 14/30/90-day chart; top pages; sources, devices and language; site searches and searches that found nothing; recent publishing.
- Visitor statistics are first-party (no GA, no cookie, no stored IP): each public page posts `{p, r, n}` to `POST /stats/hit` (`resources/js/public/siteStats.js`, sent before Alpine starts; previews and error pages opt out with `<meta name="spu-stats" content="off">`). `SiteStatsRecorderInterface` counts a visitor once a day by `HMAC(day|kind|ip|ua)` with the app key; bots, other origins, paths outside `/ar|/en` and staff intake links are dropped. Daily totals live in `site_traffic_days` forever; visitor hashes 2 days, per-page/referrer/search rows 180 days (`site-stats:prune`, daily). Reads go through `SiteStatsReportInterface`; the work lists through `AdminDashboardServiceInterface`. Config `config/site_stats.php` ("today" is Damascus time).
- Permission `site_stats.view` (editors get it by migration) gates the traffic widgets; the queue and recent publishing use the permissions of what they list. Tests: `SiteStatsTest`, `AdminDashboardTest`.
